# Phase 기획서 작성 스킬

## 목적

Preview 프로젝트(Go 기반 PR Preview 서비스)의 각 Phase에서, 코드 작성에 앞서 **논리적으로 완결된 md 기획서**를 생성한다. 리뷰어(plan-reviewer)가 회의적 관점에서 읽어도 빈틈이 없도록 설계된 템플릿을 따른다.

## 저장 위치 및 파일명 규칙

- 경로: `docs/specs/phase-{N}-{kebab-slug}.md`
- 예: `docs/specs/phase-0-scaffolding.md`, `docs/specs/phase-1-hub-webhook.md`
- 존재하지 않으면 `docs/specs/` 디렉토리 먼저 생성.

## 작성 절차

1. **선행 조사** — 기획 대상 Phase의 요구사항을 사용자 발화 또는 이전 Phase 산출물에서 전부 수집. 빈틈이 있으면 작성 시작 전에 질문을 정리해 사용자에게 확인.
2. **이전 Phase의 "다음 Phase 연결점"** 섹션을 읽고, 이번 Phase의 입력·제약으로 인용.
3. **아래 9개 섹션을 순서대로 채운다.** 빈 섹션을 남기지 않는다. 해당 Phase에 적용 불가능한 섹션이 있으면 "적용 불가, 이유: …"로 명시.
4. **교차 검토(self-pass)**: 작성 후, "plan-reviewer 체크리스트 (아래)"를 스스로 돌려본다. 통과하지 못하면 수정.
5. 저장 후 plan-reviewer에게 `SendMessage`로 리뷰 요청.

## 기획서 템플릿

```markdown
# Phase {N}: {제목}

작성일: {YYYY-MM-DD}
작성자: planner
상태: DRAFT | UNDER_REVIEW | APPROVED

## 1. Phase 개요
(1문단: 이 Phase의 목적 + 종료 시 상태)

## 2. 범위와 비범위
### 범위 (In Scope)
- ...
### 비범위 (Out of Scope — 이번 Phase에 하지 않음)
- ...

## 3. 설계 결정 및 근거
각 결정마다 4요소를 기입한다.

### 결정 1: {결정 요약}
- **결정**: ...
- **근거**: ...
- **버려진 대안**: ... (진지한 후보여야 함. 허수아비 금지)
- **되돌림 비용**: (변경 시 파급 범위)

### 결정 2: ...

## 4. 아키텍처 / 구조
- 디렉토리 트리 (이 Phase 후의 최종 형태)
- 모듈 의존 관계 다이어그램 (Mermaid 또는 ASCII)
- 필요 시 시퀀스/상태 다이어그램

## 5. 인터페이스 계약
경계면을 표로 명시한다.

### 5-1. 함수/메서드 시그니처 (있다면)
| 대상 | 시그니처 | 설명 |

### 5-2. 메시지·DTO 타입 (있다면)
| 이름 | 필드 | 타입 | 필수 | 설명 |

### 5-3. HTTP 엔드포인트 (있다면)
| 메서드 | 경로 | 요청 | 응답 | 상태코드 |

### 5-4. DB 스키마 (있다면)
| 테이블 | 컬럼 | 타입 | 제약 | 비고 |

## 6. 기능 요구사항 체크리스트
(evaluator가 하나씩 실행 가능하도록 작성)

- [ ] F-1: {요구사항} — **검증 방법**: {구체적 재현 명령/절차}
- [ ] F-2: ...

## 7. 비기능 요구사항 체크리스트
(성능·보안·이식성·관측성·유지보수성)

- [ ] NF-1: {수치·조건 기반 요구사항} — **검증 방법**: ...
- [ ] NF-2: ...

이식성 섹션은 필수 포함:
- [ ] NF-Portability-1: SQL이 SQLite·Postgres 양쪽에서 파싱된다 — **검증**: `grep` 금지어 사전(`AUTOINCREMENT`, `INSERT OR REPLACE`, `::jsonb`) 매치 0
- [ ] NF-Portability-2: DB 접근은 `internal/store` 인터페이스 경유 — **검증**: `internal/hub`·`internal/agent`에서 sqlc 생성 코드 직접 import 0건

## 8. 리스크와 완화책
(3개 이상, 구체적으로)

### 리스크 1: {이름}
- 원인: ...
- 영향: ...
- 완화책: ...
- 트리거 지표: (언제 "완화 실패"로 판정할지)

## 9. 다음 Phase 연결점
- 이번 Phase의 어떤 산출물이 다음 Phase에 쓰이는가
- 다음 Phase가 채워야 할 TODO 목록 (있다면)

---

## 리뷰 이력
- {date} — {reviewer}: {요약}
```

## 원칙

- **"적절히", "필요에 따라" 금지**: 구체적 조건/수치로 대체.
- **검증 방법 누락 금지**: 체크리스트 항목마다 "검증 방법"이 없으면 그 항목은 미완성.
- **이식성 원칙 누수 금지**: SQLite 특화 문법, sqlc 코드 직접 의존 등이 슬그머니 들어가지 않도록 섹션 3·7에서 명시.
- **비범위의 기술적 침범 감지**: "이번에 안 한다"고 선언한 것이 다이어그램이나 인터페이스에 그려져 있으면 모순. 자기 검토 단계에서 잡는다.

## 리뷰 피드백 반영 규칙

plan-reviewer가 `REQUEST_CHANGES`를 보내면:
1. 수정 요청 목록을 번호별로 응답란에 받아적고, 각 항목에 "수정 위치 (섹션)" + "수정 내용" 메모.
2. 수정 후 같은 파일 덮어쓰기. 파일 말미 "리뷰 이력"에 한 줄 추가.
3. 반박할 항목은 반박 근거를 정리해 `SendMessage`로 토론. 합의 전에 무시하고 진행 금지.

## 완료 조건

- plan-reviewer가 `APPROVE` 판정.
- 기획서 상단 상태를 `APPROVED`로 변경.
- 리더(오케스트레이터)에게 완료 통지.
