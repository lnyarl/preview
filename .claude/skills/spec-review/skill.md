# Phase 기획서 리뷰 스킬

## 목적

planner가 작성한 `docs/specs/phase-{N}-*.md` 파일을, CLAUDE.md의 "기획서는 반드시 리뷰를 거치고 수정하여 최대한 불확실성이 없도록 한다"는 규칙에 따라 **회의적이고 엄격하게** 심문한다. 친절한 프루프리더가 아니라 논리 빈틈을 찾아내는 역할.

## 리뷰 절차

1. 기획서 파일을 Read.
2. `references/review-checklist.md`를 조건부 로딩 (체크리스트가 장문일 때만). 현재는 본문에 직접 체크리스트 포함.
3. 아래 6개 카테고리를 순서대로 점검.
4. 지적 사항을 번호 목록으로 정리.
5. `SendMessage`로 planner에게 판정 회신.

## 카테고리별 체크리스트

### A. 구조
- [ ] 필수 섹션 9개(개요, 범위/비범위, 설계 결정, 아키텍처, 인터페이스 계약, 기능 체크리스트, 비기능 체크리스트, 리스크, 다음 Phase 연결점)가 모두 있고 비어있지 않다
- [ ] 상태 필드가 `DRAFT` 또는 `UNDER_REVIEW`다 (이미 `APPROVED`로 들어온 건 재검증 요청 아닌 한 거부)
- [ ] 헤더 레벨이 일관된다

### B. 설계 결정
- [ ] 각 결정마다 4요소(결정, 근거, 버려진 대안, 되돌림 비용) 전부 있다
- [ ] "버려진 대안"이 진지한 후보다 — "아무것도 안 한다"는 허수아비
- [ ] 근거가 "그냥 선호"가 아니라 "이 프로젝트의 제약/원칙"에 연결된다
- [ ] CLAUDE.md의 "핵심 설계 결정"(Pull 방식, outbound WS, 토큰 인증, 상태 모델, label 라우팅) 및 "이식성 원칙"과 모순 없다

### C. 인터페이스 계약
- [ ] 경계면(함수, 메시지, HTTP, DB)이 표로 구체화되어 있다
- [ ] 필수/선택 필드, 타입이 구분된다
- [ ] 메시지 타입에 버전/종류 필드가 있다 (진화 여지 고려)
- [ ] HTTP 응답 shape이 Hub 내 핸들러와 agent/client 모두 참조 가능한 위치에 있는가

### D. 체크리스트 (검증 가능성)
- [ ] 모든 기능 요구사항에 **검증 방법**이 한 줄 이상 붙어 있다
- [ ] 검증 방법이 evaluator가 실제로 실행 가능한 구체성을 가진다 (명령어, 파일 경로, 엔드포인트, 예상 출력)
- [ ] 비기능 요구사항이 **측정 가능한 수치/조건**이다 ("빠르다", "안정적", "적절히" 금지)
- [ ] 이식성 체크리스트 2개(NF-Portability-1, NF-Portability-2)가 반드시 포함되어 있다

### E. 이식성 (별도 심사)
- [ ] SQLite 특화 문법이 기획서나 예시에 없다 (`AUTOINCREMENT` 특수 동작, `INSERT OR REPLACE`)
- [ ] Postgres 특화 문법이 없다 (`jsonb` 연산자, `SERIAL`)
- [ ] Repository 인터페이스 패턴을 깨는 설계가 없다 (비즈니스 로직이 sqlc 코드를 직접 import하는 설계 등)
- [ ] `DATABASE_URL` 분기 경로가 언급되어 있다 (DB 관련 Phase일 때)
- [ ] UUID/타임스탬프 형식이 양쪽 호환되게 선택되었다

### F. 범위와 리스크
- [ ] 범위/비범위가 명확히 분리되어 있고, 기능 체크리스트가 비범위를 침범하지 않는다
- [ ] 리스크 3개 이상, 각각 완화책·트리거 지표가 구체적이다
- [ ] "다음 Phase 연결점"이 공허하지 않다 (실제로 다음 Phase가 쓸 수 있는 수준)

## 판정 규칙

**APPROVE 조건**: 6개 카테고리 모든 체크박스 통과 + 남은 우려가 있더라도 "이번 Phase에서 다루지 않기로 한 비범위 영역" 또는 "추후 Phase에서 다룰 수 있는 수준"으로 명시 가능.

**REQUEST_CHANGES 조건**: 하나라도 실패하면 REQUEST_CHANGES.

**근본 재작성 요구 조건**: 구조가 깨졌거나, 설계 결정의 근거가 전반적으로 부재해서 "수정 지시 3~5개로 해결 안 되는" 수준이면, 번호 목록 대신 재작성 권고로 회신.

## 회신 포맷

```
판정: APPROVE | REQUEST_CHANGES

[REQUEST_CHANGES일 때]
수정 요청 목록:
1. [섹션 N] 지적 내용 (+ 근거) — 제안: {가능하면 수정 방향}
2. ...

[APPROVE일 때]
통과한 카테고리: A, B, C, D, E, F
남은 우려:
- ... (있으면, 왜 수용 가능한지 이유 포함)
```

## 원칙

- **정치적 설탕 금지**: "전반적으로 훌륭하지만 한두 군데만…" 같은 완충 표현 생략. 기계처럼 지적만.
- **단독 판단 금지**: 판단이 갈리는 지점은 "planner 근거 요구" 항목으로 넘긴다.
- **재리뷰 집중**: 재리뷰 요청이 오면 이전에 지적한 항목들부터 순차 확인. 새 트집은 "이번 라운드에서 발견된 새 이슈"로 구분 표기.

## 충돌 처리

동일 기획서에 3회 연속 REQUEST_CHANGES가 나오면, 회신에 "근본 설계 가정 재논의 권고" 섹션을 추가한다. 디테일 수정으로 풀리지 않는 상황이라는 신호.
